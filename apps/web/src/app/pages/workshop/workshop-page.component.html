Give your coding agent browser context

Chrome DevTools MCP lets your agent inspect pages, reproduce interactions, read console and network activity, and record performance traces. By default it launches a browser session it controls; connecting to an already-running Chrome requires remote debugging.

One-time setup

Connect Chrome DevTools MCP to Codex

Run these commands in a terminal where Codex is installed. The MCP server gives Codex browser tools for inspecting pages, reproducing issues, and recording performance traces.

  1. Make sure Node.js and Chrome are installed.
  2. Add the server to your Codex configuration: 
    codex mcp add chrome-devtools -- npx chrome-devtools-mcp@latest
  3. Confirm it is listed: 
    codex mcp list
  4. Restart Codex or start a new session so the browser tools load.

Codex shares MCP configuration between the CLI and IDE extension, so this setup applies to both.

Use an already-running Chrome browser

Start Chrome with remote debugging enabled on port 9222, then add the browser URL argument to the Codex command:

codex mcp add chrome-devtools -- npx chrome-devtools-mcp@latest --browser-url=http://127.0.0.1:9222

Keep remote debugging enabled only while you need it; the port allows local applications to control that Chrome session.

Connect Chrome DevTools MCP to Claude

Run these commands in a terminal where Claude Code is installed:

  1. Make sure Node.js and Chrome are installed.
  2. Add the server to your user configuration so it is available across projects:

  3. Confirm the server connection:

  4. In Claude Code, run /mcp to view the server status and available tools.

Try it out

Prompt examples

Keep the page open in Chrome and describe what you want the agent to investigate.

Diagnose a slow interaction

On the current Performance page, record a trace and click Refresh Dashboard. Diagnose the delay, identify the longest main-thread work, check whether network activity contributes, and point me to the relevant source code. Don’t change any files.

Find a slow or failing request

Reproduce the problem on the current page. Inspect the network requests and identify any failed or unusually slow request. Explain its status and timing, then trace it to the code that made the request.

Diagnose repeated SignalR requests

On the Network Debugging page, select the SignalR Request Loop scenario and open the Backend activity panel. Use DevTools to find and highlight the repeated SignalR negotiate and polling requests, then compare them with the panel’s numbered loop iterations. Trace the loop to its source, explain why the requests keep recurring, and tell me how to stop the scenario. Don’t change any files.

Investigate a browser error

Reproduce the issue on the current page, inspect the console for related errors or warnings, and use the stack trace to find the responsible code. Explain what the evidence shows before suggesting a fix.

Check a mobile layout

Inspect this page at a 390px mobile viewport. Look for clipped content, horizontal overflow, or controls that are hard to use. Show me a screenshot and describe the specific elements that need attention.
